API Contract & Team Integration Guide

This is the shared guide for frontend, backend, AI/ML and QA members. It explains how the app parts communicate, what the API examples mean, how to use mock data while working in parallel, and how to integrate safely.

Goal: everyone should agree on the same endpoint paths, field names, data formats and error behaviour before building connected features.
Important status note: The supplied Product Document defines the architecture and API route families, but it does not contain a complete schema for every endpoint. The paths below follow that document. JSON examples marked as examples/proposed must be confirmed by the backend owner in FastAPI/Pydantic and the generated OpenAPI schema. This document does not claim that every listed endpoint is already implemented.

1. First understand what an API is

Frontend

The screens users see: forms, expense lists, dashboard and buttons. The frontend sends requests to the backend and displays the response.

Backend

The FastAPI server receives requests, checks input and permissions, runs business rules, reads/writes PostgreSQL, and returns JSON.

Database

PostgreSQL stores the actual accounts, expenses and other records. A successful-looking screen alone does not prove data was saved.

API contract

The agreement that says which URL and method to call, which fields to send, what comes back, and which errors can happen.

Example: when a user adds lunch costing ₹250, the frontend sends an expense request. The backend validates it, checks the signed-in user, saves it to PostgreSQL, and returns the saved expense with its ID. The frontend then displays the server response.

4. JSON examples for frontend and backend

These examples are proposed initial shapes for team agreement. The backend owner must encode the final request and response models in Pydantic/OpenAPI. If the real implementation differs, update the contract and frontend together—do not quietly maintain two different formats.

4.1 Register — POST /api/v1/auth/register

{
  "email": "alex@example.com",
  "password": "example-password",
  "display_name": "Alex",
  "remember_me": false
}

Expected success: 201 Created. Return only safe profile fields and issue the agreed session cookie. Never return a password, password hash or session secret in JSON.

{
  "data": {
    "id": "usr_opaque_id",
    "email": "alex@example.com",
    "display_name": "Alex"
  }
}

4.2 Login — POST /api/v1/auth/login

{
  "email": "alex@example.com",
  "password": "example-password",
  "remember_me": true
}

Expected success: 200 OK, with session cookie and safe user profile. Invalid credentials should return a generic 401 response.

4.3 Create a personal expense — POST /api/v1/expenses

Send header Idempotency-Key: <unique-key>.

{
  "amount_paise": 25000,
  "description": "Lunch",
  "category_id": "cat_food",
  "occurred_on": "2026-10-22",
  "notes": null
}

Expected success: 201 Created. The server returns the saved record, including its ID, version and timestamps.

{
  "data": {
    "id": "exp_opaque_id",
    "amount_paise": 25000,
    "description": "Lunch",
    "category_id": "cat_food",
    "occurred_on": "2026-10-22",
    "version": 1,
    "created_at": "2026-10-22T08:30:00Z",
    "updated_at": "2026-10-22T08:30:00Z"
  }
}

4.4 List expenses — GET /api/v1/expenses

Possible query parameters: from, to, category_id, q, limit, cursor. The server must return only expenses the signed-in user may access.

{
  "data": [
    {
      "id": "exp_opaque_id",
      "amount_paise": 25000,
      "description": "Lunch",
      "category_id": "cat_food",
      "occurred_on": "2026-10-22",
      "version": 1
    }
  ],
  "meta": { "next_cursor": null }
}

4.5 Edit an expense — PATCH /api/v1/expenses/{id}

{
  "version": 1,
  "description": "Lunch with team",
  "amount_paise": 27000
}

The server returns the updated record and increments its version. A stale version returns 409 Conflict. The client must not be allowed to change protected fields such as user_id or roles.

4.6 Delete and restore

  • DELETE /api/v1/expenses/{id} — proposed soft delete.
  • POST /api/v1/expenses/{id}/restore — restore only if allowed by policy.

The frontend should show success only after the server confirms it. If the request fails, keep the screen consistent with the server state.

4.7 Category suggestion — POST /api/v1/ai/category-suggestion

{
  "description": "Uber ride to campus",
  "merchant": "Uber"
}

Proposed response:

{
  "data": {
    "suggested_category_id": "cat_transport",
    "confidence": 0.91,
    "requires_confirmation": true
  }
}

The suggested category must exist in GET /api/v1/categories. If the model is unavailable or uncertain, the user must still be able to choose a category manually. The app must not silently save an AI suggestion without user confirmation.

4.8 Sync — GET /api/v1/sync?since=2026-10-22T08:00:00Z

{
  "data": {
    "changes": [
      {
        "entity_type": "expense",
        "id": "exp_opaque_id",
        "operation": "upsert",
        "version": 2,
        "updated_at": "2026-10-22T08:30:00Z"
      }
    ],
    "next_since": "2026-10-22T08:30:00Z"
  }
}

This is a proposed response. Backend must confirm cursor semantics and how deletions are represented. Sync must never return another user's private records.

4.9 Group expense — planned for Sprint 2, not a Sprint 1 dependency

POST /api/v1/groups/{id}/expenses

{
  "amount_paise": 300000,
  "description": "Groceries",
  "category_id": "cat_groceries",
  "occurred_on": "2026-10-22",
  "paid_by_user_id": "usr_alex",
  "participant_user_ids": ["usr_alex", "usr_blair", "usr_casey"],
  "split_mode": "equal"
}

Product rule: equal splits must allocate paise using the largest-remainder method. The expense, payment, shares and audit event must be written in one database transaction; if any write fails, roll back all writes.

5. Standard error behaviour

The response envelope below is a proposed convention. If the existing API already uses another envelope, the backend owner must document it and keep it consistent rather than introduce two formats.

{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Please check the submitted fields.",
    "field_errors": {
      "amount_paise": "Must be greater than zero."
    }
  },
  "meta": { "request_id": "req_opaque_id" }
}
StatusMeaningFrontend response
400Malformed or invalid operationShow useful message; keep entered values.
401Not signed in / session expiredShow sign-in flow; do not assume identity.
404Not found or not allowed to viewShow unavailable item; do not reveal whether private record exists.
409Duplicate/idempotency conflict or stale versionExplain conflict; refresh or retry safely.
422Request validation failedShow field-level errors next to inputs.
429Rate limit reachedSuggest waiting; do not rapidly repeat requests.
500Unexpected server failureShow a generic message and request ID; never show stack traces.

6. How frontend and backend can work in parallel

  1. Agree on the contract first. Confirm method, path, request fields, response fields, status codes and authentication for each Sprint 1 endpoint.
  2. Frontend uses mock data. Keep sample JSON in a dedicated mock/service module. Label it as mock and never show a fake save as if it were stored in PostgreSQL.
  3. Backend implements the same schema. Define Pydantic request/response models, implement routes/services and expose OpenAPI.
  4. Compare against OpenAPI. If field names or response shapes differ, agree the change and update both sides. Prefer generating frontend TypeScript types from OpenAPI.
  5. Switch the API adapter. Keep screen code separate from the mock service so integration means changing configuration/client, not rewriting every screen.
  6. Test real persistence. Create an expense, confirm the server response, reload/list it from the backend, and verify it is in the database.
Simple example: frontend can show a sample “Lunch ₹250” card using mock data while backend builds POST /api/v1/expenses. Before integration, both agree that the API sends amount_paise: 25000, not amount: 250. Later the frontend switches to the real API client.

7. Security and implementation rules

  • Use one shared frontend API client and one configured base URL; do not hard-code a developer's localhost URL into production code.
  • For cookie authentication, verify credentials, CORS and CSRF settings in the actual target runtime.
  • Never store passwords or session secrets in frontend source code or commit secrets to GitHub.
  • Backend routes should stay thin: authenticate, authorize, validate, then call the service layer.
  • Use Pydantic models for requests and responses; do not trust fields simply because the frontend sent them.
  • Load ID-based records through the shared policy module before reading or changing them.
  • Use transactions for multi-record writes and roll back all related writes if one fails.
  • Do not calculate authoritative balances in the frontend. The backend ledger is authoritative; UI calculations are only previews.
  • AI must not be part of the ledger arithmetic. Keep manual/rule-based fallback behaviour available.
  • Keep mock mode separate and disable it in the final integrated path.

8. Final integration checklist

  • Frontend and backend agree on every endpoint used in Sprint 1.
  • Request/response models are documented and match the generated OpenAPI schema.
  • Authentication and session behaviour works in the actual runtime.
  • Expense creation uses integer paise and an idempotency key.
  • Expense lists contain only records the signed-in user may access.
  • Invalid input returns useful field errors and preserves form data.
  • Delete/restore UI reflects the actual server result.
  • AI category suggestions never block manual selection.
  • Sync cursor and deletion behaviour are documented before relying on sync.
  • Tests cover valid input, invalid input, unauthenticated requests, unauthorized IDs, repeated requests and database failures.
  • Mock data is disabled or removed from the final integrated flow.
  • Relevant CI checks pass and pull requests have been reviewed.
Do not mark an endpoint as complete just because it appears in this document. It is complete only when implemented, documented in OpenAPI, tested and integrated as required by its sprint.
